# Android 原生化项目规划

> **简体中文** | [English](../project-plan.md)

更新日期：2026-10-24。本文随规划讨论更新，区分已确认决定、阶段性选择和待讨论事项。

## 项目出发点与已确认方向

- 官方 QQ 音乐过于臃肿，希望开发一个适合自己使用的第三方客户端。
- 核心用途：听歌。当前阶段先完整移植旧 Android 客户端的功能、交互与设置。
- 产品目标平台为 Android；后续规划围绕 Android 使用体验展开。
- 旧技术栈过多、过重，需要减少开发、构建和维护负担。
- 使用 Android 原生界面，当前以 Kotlin / Jetpack Compose 为界面技术。
- 用文档记录范围、架构决策和验收要求，约束后续开发。

Android 单平台定位不等于现在删除桌面代码、旧客户端或发布工作流；这些内容的退出方式仍需规划。

## 产品范围：先完整移植旧 Android 客户端

用户已明确当前原生版缺失过多，希望先把原来的软件完整移植为 Android 原生版。
此前将“就是听歌”解释为精简旧功能的规划已修正。

- 以旧 Android 客户端实际开放的用户能力为基准，逐项恢复页面、操作、设置、状态反馈与交付路径。
- 歌词、外观、账号、统计、诊断及更新等旧版能力均纳入对齐清单；不按助手推测的使用频率降为可选需求。
- 复用现有 Rust 核心，以 Kotlin / Compose 承接原生界面与 Android 交互。
- 保留原有信息层级、操作意图与可配置性；原生适配不能静默省略用户能力。具体视觉细节随对应模块核对。
- 轻量化通过减少技术栈和工程负担推进；功能精简留在完整移植之后另行讨论。

范围账本见[完整移植对齐清单](native-parity.md)。清单中的缺失项属于迁移待办，按下文已确认的六个批次推进。
旧 Android 已关闭的桌面能力单列，避免与迁移遗漏混淆。原生版独立包名与旧账号数据的兼容方案仍需确定。

## 决策 D001：阶段性保留 Rust 核心

状态：**暂定采用，可复审**。决定日期：2026-10-23。

当前采用 Kotlin / Compose 原生界面，通过 JNI 复用现有 Rust 核心。
用户更倾向最终全部使用 Android 原生技术，但考虑重写工作量，先保留 Rust。
用户对刚完成测试的观察是差异似乎不大，因此目前没有足够理由为全部 Kotlin 重写投入额外工作。

证据边界：这属于阶段性选择。现有原生模块比较的是原生界面与旧 Web 界面，复用了同一 Rust 核心；
不能据此认定 Kotlin / Rust 与全 Kotlin 实现的性能、耗电或维护成本相同。
既有设备观察和限制见[原生模块检查点](../../apps/android/android/nativeApp/README.md)。

开发约束：

- 新界面工作以原生 Android 模块为落点。
- 复用有价值的 Rust 能力，对齐旧 Android 已开放的功能；具体实现结构按原生工程需要调整。
- 新能力在 Android 与 Rust 之间的归属，按职责、实现成本和维护成本决定；避免两侧重复持有业务状态。
- 构建链精简仍是后续工作。当前 APK 的原生界面不代表仓库已摆脱 Node、Capacitor 或旧工程配置。

复审条件：出现可复现的 JNI / Rust 维护障碍、构建负担或性能问题，或有具体收益足以覆盖 Kotlin 重写成本时，
重新比较方案。复审以具体问题和证据为依据，不预先安排全量重写，也不要求为本次决定先实现全 Kotlin 对照版。

## 当前开发约束

完整移植阶段，每项工作应关联对齐清单编号；用户入口、交互、设置、状态和验证证据分别核对。
Rust 已有实现、原生页面同名、构建通过都不能单独作为完整迁移的完成条件。

1. 开始一项工作前明确目标、范围和可观察的验收条件。小改动在任务说明中写清即可，无需另建文档。
2. 区分用户已确认的要求、助手建议和待讨论事项；不将待讨论内容当作实施授权。
3. 技术选型或范围变化先补充决策理由，再实施受影响的工作；目标与授权清楚时直接推进。
4. 实现保持聚焦。引入新依赖或抽象时说明解决的问题和维护代价。
5. 按改动风险验证，分别记录自动化检查、构建、真机与真实账号验证；未执行的检查明确标注。
6. 完成时同步受影响的文档。规划目标、代码现状和验证结果分别描述。

现有账号凭据保护、日志脱敏、播放权益及许可证约束继续适用。

### 已确认差异：保留当前原生版返回逻辑

用户最终明确要求按当前原生版逻辑保留。以当前源码为基线：

- 切换根入口时清空原生页面返回栈；打开普通页面时记录来源页面。
- 非首页的系统返回先尝试返回栈，栈空时进入首页；首页交由 Android 默认返回行为处理。
- 非根页面的顶部返回按钮先尝试返回栈，栈空时进入首页。

依据：[NativeApp](../../apps/android/android/nativeApp/src/main/java/org/yaqmc/android/nativeui/NativeApp.kt) 的返回处理与
[NativeViewModel](../../apps/android/android/nativeApp/src/main/java/org/yaqmc/android/nativeui/NativeViewModel.kt) 的 `navigate` / `back`。
此处定义保留的源码行为，第一批验证结果见下文；不为对齐旧版而增加返回规则。

第一批实施顺序为：核对入口与文案 → 建立主题 / 语言的偏好保存与读取 → 对齐导航与顶部入口 → 验收。
具体类拆分、持久化库和导航库按实现需要选择，不在规划中预设新增依赖。

完成记录应包含上述任务结果、涉及的对齐编号、检查命令与结果、设备 / 屏幕条件和对比证据。
自动检查重点覆盖返回决策、主题解析、语言回退及偏好读写；构建与真机检查分别记录。
真机核对手机窄屏和宽屏布局、三种主题、三种语言、重启保存及现有播放路径。
尚未执行的验收保留待验收状态。旧包名升级、跨应用账号与数据迁移留在第六批决定。

### A01 登录失败跟进（2026-10-24）

真实手机授权能够跳转官方 QQ 音乐并收到确认；两次凭据交换均返回业务码 `20279`（登录设备数量超限），
官方设备管理页显示当前登录设备数为 5。原实现丢失业务码，导致显示通用“授权响应异常”。
修正为在账号失败快照中保留可选 `upstreamCode`，原生界面针对 `20279` 显示设备限制及处理方法；
保留旧快照兼容，不把此失败当作用户拒绝授权或登录成功。

同时修复手机授权每次新建随机设备身份的问题：安装实例使用提供器设置持久保存自己的虚拟设备信息，
重试复用同一客户端，重建后恢复同一身份；二维码请求后保存已更新的设备信息。
身份读写失败时停止发起新请求，避免静默生成另一身份；缓存清理和注销不删除该设置。
这项修复不能自动解除已触发的服务端设备限制；是否移除旧设备由用户决定。

验证结果：提供器 Rust 单元测试 282 项通过、8 项忽略；原生单元测试 24 项通过；lint 为 0 错误、32 条警告。
本轮真机针对性回归 7 项通过，包含新设备限制提示、1 项真实提供器和原有 5 项壳层检查。
ARM64 Rust 核心已重新编译；debug 与 benchmark APK 内的 Core SHA-256 一致。
首次构建曾遇 Windows 临时目录写入拒绝，改用项目内临时目录；后续重叠构建损坏 Kotlin 增量缓存，
清理相应构建缓存并关闭增量编译后串行构建通过。最终构建与安装均成功，不将失败的尝试算作通过。

随后覆盖安装优化 benchmark 包并冷启动，界面仍为已登录，确认本轮会话恢复成功。
