# 项目规划

更新日期：2026-10-29。本文维护产品方向、范围、关键决定与工作安排；建议、阶段性选择和已确认决定分别标明。

## 目标与范围

官方 QQ 音乐过于臃肿，因此开发一个适合自己使用的 Android 客户端。主要开发者是自己，软件体验与工程维护都应保持轻量。

- 只围绕 Android 规划产品，使用 Kotlin / Jetpack Compose 原生界面。
- 当前先完整移植旧 Android 已开放的功能、交互和设置，保留原有信息层级、操作意图与可配置性。
- 歌词、外观、账号、统计、诊断、更新等均在移植范围；听歌用途不构成删减旧功能的依据。
- 轻量化先通过减少技术栈和工程负担推进。功能精简留在完整移植之后另行讨论。
- 旧 Android 未开放的桌面能力单列，不能仅凭共享代码存在就算作迁移需求。

范围与完成状态统一由[迁移对齐清单](native-parity.md)维护。2026-10-29 用户明确要求清理旧工程，仅保留移植后的 Android 工程；本次不包含迁移用户数据或发布产物。

## 已确认与阶段性决定

### D001：阶段性保留 Rust 核心

2026-10-23，暂定采用，可复审。当前以 Kotlin / Compose 承接界面，通过 JNI 复用已有 Rust Core。
用户更倾向最终使用 Android 原生技术，考虑重写工作量后先保留 Rust，不预先安排全 Kotlin 重写。

新界面在 `nativeApp` 实现。Android 与 Rust 按职责、实现和维护成本分工，避免重复持有业务状态；具体边界尚未全部定案。
现有比较复用了同一 Rust 核心，不能据此认定混合实现与全 Kotlin 的性能、耗电或维护成本相同。
出现可复现的 JNI / Rust 维护障碍、构建负担或性能问题，或收益足以覆盖重写成本时，再据证据复审。

### 已确认差异：保留当前原生版返回行为

- 切换根入口时清空页面返回栈；打开普通页面时记录来源。
- 非首页的系统返回先尝试返回栈，栈空进入首页；首页交由 Android 默认处理。
- 非根页面的顶部返回按钮先尝试返回栈，栈空进入首页。

源码基线见 [NativeApp](../../apps/android/android/nativeApp/src/main/java/org/yaqmc/android/nativeui/NativeApp.kt) 与
[NativeViewModel](../../apps/android/android/nativeApp/src/main/java/org/yaqmc/android/nativeui/NativeViewModel.kt)。不为对齐旧版另外增加返回规则。

### D003：长期开发与协作原则

2026-10-27，已确认。用户负责表达目标、体验偏好和重要取舍；开发者负责将其转化为合理、统一、可维护的实现，主动发现用户不应需要提前穷举的问题。以下原则适用于网页端开发和本地审查，具体执行与检查方式见[开发指南](development.md)的“开发与审查约定”。

- **从使用目标出发。** 先理解用户要完成的事情，结合现有能力提出推荐方案。常规技术细节自行判断；涉及范围、明显体验差异或长期维护成本的选择，用日常语言解释取舍后对齐，不将模糊要求直接扩展成复杂系统。
- **保证基本可用性与一致性。** 遵循 Android 常见交互惯例，统一同类控件、反馈和操作路径。基本可用性由开发者主动把关，审美偏好和产品取舍与用户讨论。完整移植保留功能、操作意图与可配置性，具体实现可按原生平台调整；明显交互变化需对齐，不借简化删减功能。
- **面向使用者表达。** 页面、设置、错误提示和更新说明讲清发生了什么、用户可以做什么；不直接暴露内部状态名、参数名或开发术语。必要技术信息放在可展开详情或诊断入口，已提供的诊断能力继续保留。
- **控制实现复杂度。** 优先复用现有能力和组件，明确业务状态与数据归属。新增依赖、持久化数据、跨层接口或通用抽象须解决当前具体问题，不为尚未确定的未来需求提前搭建机制。
- **以实际行为验收。** 功能存在、测试通过之后仍需检查用户能否顺利完成操作；保存、取消、失败、重试和恢复的表现应与实际结果一致。界面看实际呈现，跨层功能检查相关链路。
- **持续维护共同约定。** 修复问题时检查同类原因，优先在共同组件或责任源头解决。只同步受影响的测试和主文档；超出本次范围的同类问题说明后续安排，不自行扩大改动。

规范应说明适用时机、具体行动和检查方式；无法影响实际决定的空泛条款应重写或删除。小修复采用短流程，检查深度随影响范围调整，不要求每次填表、写设计报告或运行全量测试。

## 已确认的迁移顺序

按“核对旧 Android 行为 → 原生实现 → 针对性检查 → 真机验收”推进，完整移植总范围不变。

| 批次 | 内容                                                                         | 对齐编号与边界                                                              |
| ---- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 1    | 基础与整体界面：导航、顶部入口、主题、语言、偏好基础                         | N01、N02、O01、O05；T05 的保存基础；返回按已确认差异                        |
| 2    | 浏览与账号：首页、发现、搜索、详情、登录、会员、音乐库与歌单操作             | N03、H01–H02、D01–D02、S01–S04、C01–C05、A01–A07；播放器 / 队列入口随第三批 |
| 3    | 播放器与队列：控制、音质反馈、推荐续播、排序、下一首播放、分享和系统媒体集成 | P01–P06、I01–I02；补齐 H02 播放 / 补歌联调和 N03 专属入口                   |
| 4    | 歌词与个性化：逐字效果、布局与预设编辑、配色、背景、字体                     | L01–L05、O02–O04；相关 T05 保存与兼容                                       |
| 5    | 统计与维护：统计、缓存、诊断、问题报告、更新与关于                           | T01–T04；相关 T05 偏好                                                      |
| 6    | 交付与替换：构建、签名、升级、数据兼容与完整回归                             | T05–T06；复核适用项后确定旧版替换安排                                       |

跨批次项按细项记录，不能因为部分实现就关闭整个编号。各批使用当前原生构建入口检查，不等第六批才验证原生包。
近期按清单继续迁移，第三至第六批的具体任务与验收条件随对应工作细化，不提前增加独立排期文档。
